A 14 MB vision model that holds up on real farm photos

Problem

Many plant-disease models are trained and scored on lab photos: one leaf, plain background, even light. Farmers’ photos look nothing like that, and a diagnosis on its own doesn’t tell anyone what to do next.

What I built

Two MobileNetV2 transfer-learning classifiers (8 tomato conditions, 4 banana classes) behind a Flask pipeline. After the model runs, the pipeline pulls a 5-day forecast, estimates the crop’s growth stage, schedules field work around the weather (sprays move off rainy days), puts a rupee figure on the expected yield loss, and gives treatment advice in the farmer’s language, picked from their city and read aloud in the browser.

Results · banana model, field images

accuracy on a 185-image validation split
95.1%
weighted F1; the classes are imbalanced
0.95
model size, about 7× smaller than ResNet50
14 MB
fewer irrigation runs in a 30-day weather simulation
40%

Decisions & failure analysis

  • Evaluated on field images. The banana model is trained on BananaLSD, a field-collected dataset with cluttered backgrounds and natural light, so the score reflects the photos farmers actually take.
  • Reported F1, not just accuracy. Sigatoka is half of the dataset, so accuracy on its own would flatter the model.
  • Where it fails: 7 of the 9 validation errors were predicted as Sigatoka, the majority class, and healthy leaves have the lowest recall (0.84). That’s the error pattern class rebalancing would target.
  • Small enough to run anywhere. MobileNetV2 weighs about 14 MB against about 98 MB for ResNet50, and the app serves on CPU-only TensorFlow.

Reel Intelligence: an LLM agent that reads intent, not keywords

Problem

Recommend genuinely useful learning content from a student’s Instagram Reel history. Keyword matching fails here: a Java meme, a “day in the life of a software engineer” vlog and an interview joke aren’t a request for more Java. Together, they point to an interest in software engineering as a career.

What I built

A three-stage reasoning pipeline. It reads each reel’s surface topic and underlying signal, clusters the signals across all reels into one interest, then generates a recommendation that has to pass a hype filter: no listicles, no FOMO, no vague promises. Every answer comes back in a fixed 8-field format with its reasoning and a confidence level.

Decisions

  • One call instead of ten. The stages share context inside a single prompt with a strict output format. That cut quota use by 90% and kept latency inside the 60-second function limit.
  • Fail over, don’t fail. A key-rotation state machine switches API keys on 429 (quota) and 503 (overload) instead of returning an error.
  • Test the contract, not the model. 21 schema and integration tests run against mocked responses, so CI checks every stage’s output shape without spending quota.

RGMCET Eduflow: from class project to the platform my campus uses

What it is

What started as a class project is now RGMCET’s campus-wide student platform (live as RGM ManageBAC), used by about 5,000 students and 30–40 faculty. It was built by a team of three; I designed the AWS architecture and owned the cloud deployment end to end.

Scale

Design

  • RDS Proxy between Lambda and PostgreSQL. Serverless functions scale out fast and each one wants a database connection. The proxy pools them, so traffic bursts don’t exhaust the database.
  • Compute and data inside a VPC. Lambda and the database run inside a VPC, with IAM roles scoping what each piece can touch.
  • Managed sign-in. Cognito handles accounts and tokens rather than custom authentication code.

Finding which stage of a pipeline caused the drift

Problem

Most monitoring raises one alarm at the model’s output: drift detected. It doesn’t say whether the cause was bad incoming data, a preprocessing change or the model itself, which is the first thing whoever is on call needs to know.

Design

Watch three stages separately. Raw ingestion and preprocessed features get two-sample KS tests; predictions get ADWIN, a streaming change detector. Each monitor records drift magnitude and onset time, and an attribution engine ranks the stages by magnitude × 1 / onset lag: the stage that drifted hardest and earliest is the likeliest root cause. Confirmed drift then has to pass a cost-benefit gate and a human approval before any retraining.

Shipped so far

Phase 1 is the full core lifecycle: CSV ingestion with schema validation and per-column baseline statistics; preprocessing; Random Forest, XGBoost and Logistic Regression trained in parallel on Celery workers; side-by-side comparison on accuracy, F1 and latency; a staging → production model registry; and a serving API that logs every prediction as the future drift baseline.
